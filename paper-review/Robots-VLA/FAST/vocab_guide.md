# 词表与分词详解：从 LLM 怎么"读"文字，到 FAST 怎么"读"动作

> **主题**：词表（Vocabulary）和分词（Tokenization）——LLM 的基础设施，如何被 FAST 迁移到动作空间
> **用途**：理解为什么 FAST 要把连续动作变成离散 token，以及整个映射链是怎么工作的
> **关联文档**：[π₀-FAST 论文导读](./fast_paper_guide.md) · [DCT 详解](./dct_guide.md) · [BPE 详解](./bpe_guide.md)

---

## 读之前先搞清楚

### 为什么需要"词表"？

LLM 不认识文字——它只认识数字。你输入 "叠衣服"，模型内部看到的是一串整数，比如 `[23456, 12890]`。

**词表就是把"人类能读的文字"和"模型能算的数字"对应起来的一张表**——就像字典给每个汉字编了一个页码。

同样，FAST 要训练一个 VLA（也是个 Transformer），但 VLA 不认识关节角度——它也只认识整数。FAST 做的事情本质上就是：**给动作也编一本"字典"。**

> **小白理解**：LLM 像一个只会读数字的外国人。你写"hello"，它不认识——你得先查字典，把 "hello" 翻译成它认识的数字，比如 15496。它算完之后，输出另一个数字 320，你再查字典翻译回 "world"。**FAST 给机器人的"关节角度"也编了这样一本字典。**

### 阅读本文需要的前置知识

| 概念 | 简单解释 |
|:---|:---|
| **Transformer** | LLM 的基础架构——输入一串整数，输出一串整数 |
| **Token** | 文本/数据的最小处理单位——不是字母，是"词片" |
| **Embedding** | 把 token ID 变成一个高维向量（如 4096 维），让模型能理解 token 之间的关系 |
| **Softmax** | 模型的最后一层——输出一个词表大小的向量，每个位置是"下一个 token 是这个的概率" |

## 一、LLM 的词表是怎么回事

### 1.1 GPT 怎么"读"文字？

以 GPT-2 为例，它的词表有 50257 个 token。每个 token 是一个整数 ID。

你输入 `"I love robots"`，GPT 内部实际处理的是：

```
"I love robots"
    │
    ▼  tokenizer（分词器）
["I", " love", " robots"]     ← 切成 3 个 token
    │
    ▼  查词表（vocabulary lookup）
[40, 1842, 23569]              ← 3 个整数 ID
    │
    ▼  embedding（嵌入）
3 个 768 维向量                ← 模型真正算的
```

推理时反过来：

```
模型输出: logits (50257 维向量，每个位置是一个概率)
    │
    ▼  argmax — 概率最高的位置
token ID = 23569
    │
    ▼  查词表反向
" robots"
```

### 1.2 词表长什么样？

GPT-2 词表的前 20 个 token 大致是：

| Token ID | 内容 | 说明 |
|:---:|:---|:---|
| 0 | `!` | 感叹号 |
| 1 | `"` | 双引号 |
| ... | ... | 各种标点和特殊字符 |
| 30 | `a` | 单个字母 |
| 31 | `b` | — |
| ... | ... | |
| 256 | `t` | |
| ... | ... | |
| 1000+ | `the` | 常见单词——BPE 合并的结果 |
| 1842 | ` love` | 带前导空格的 "love" |
| 50000+ | `Ġrobot` | 带特殊标记的 " robot" |

> **关键观察**：词表里既有单字母（`a`, `b`, `t`），也有常见单词（`the`），还有带空格的单词片段（` love`）。这是 BPE 训练的结果——高频组合被合并成了单个 token。

### 1.3 词表大小的 trade-off

| 词表大小 | 优点 | 缺点 |
|:---|:---|:---|
| **小**（几千） | 训练快，参数少 | 每个 token 信息量少，序列长——"hello" 要切成 "h-e-l-l-o" 5 个 token |
| **大**（几十万） | 序列短，每个 token 信息量大 | 最后一层 softmax 计算量大，训练慢 |
| **适中**（3-10 万） | LLM 的工程甜点 | — |

GPT-2 选 50257，GPT-4 约 10 万，PaliGemma（FAST 用的 VLM）约 25.7 万。

## 二、FAST 的三层"词表"

FAST 不是简单地把动作值映射到一个现成的词表——它构建了**三层递进的"字典体系"**，每一层解决不同的问题。

```
原始 action chunk (50步×32维, 1600个连续浮点数)
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│  第一层：量化字典（人工设定）                                    │
│                                                                  │
│  作用: 把连续小数 → 离散整数                                     │
│  词表: {..., -2, -1, 0, 1, 2, ...}（档位间隔决定词表大小）     │
│  设计: 低频系数给 256 档（精细），高频给 1 档（直接归零）       │
│                                                                  │
│  "256 档"和"1 档"的区别:                                         │
│    · 256 档（k=0, 最重要）: DCT 系数在 [-3, 3] 范围 → 切成     │
│      256 个格子，每格宽度 6/256≈0.023 → 精度小数点后两位       │
│      例: 2.93 → quant(2.93) = 29（第 29 格）                   │
│    · 1 档（k=4+, 噪声）: 只有一个格子——"0"。不管原始值           │
│      是多少（0.03、-0.01、0.001），全部归零 → 直接丢弃         │
│    · 中间档位（k=1~3）: 随 k 增大档位数递减——256→128→64→32    │
│                                                                  │
│  像考试打分——主科（语数外）给百分制，副科给及格制，            │
│    课间操不打分。DCT 排好了重要性，后面的"没分"直接放弃        │
│                                                                  │
│  例: [2.93, -1.81, -0.12, 0.03, -0.01]                           │
│   → [29,   -18,   -1,    0,    0]                                │
│                                                                  │
│  为什么手动设计: 频率系数的范围是已知的（[-3, 3]左右），         │
│    不需要从数据中学习——数学告诉你边界在哪                       │
└──────────────────────────────┬──────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│  第二层：BPE 词表（从 1M 条 action 数据中学习）                  │
│                                                                  │
│  作用: 把频繁一起出现的整数序列 → 合并为单个 token               │
│  词表: ~1000-5000 个 token（典型 FAST 配置）                     │
│  设计: BPE 自动发现"运动词汇"                                   │
│                                                                  │
│  例: [29, -18] 频繁一起出现 → token #156                        │
│      [0, 0, 0, 0, 0] 极常见 → token #512                        │
│                                                                  │
│  30-60 个整数 → 30-60 个 FAST token（这层不减少数量，            │
│    但让模型学的是"运动语义"而非"原始数值"）                     │
└──────────────────────────────┬──────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│  第三层：PaliGemma 词表映射（工程适配）                          │
│                                                                  │
│  作用: 把 FAST token ID → PaliGemma 词表里的位置                 │
│  词表: PaliGemma 的 257152 个 token                              │
│  设计: FAST token 映射到 PaliGemma 词表的最后一段                │
│        （词表最后 128 个是特殊 token，FAST 用它们之前的空间）    │
│                                                                  │
│  映射公式（GitHub 源码 tokenizer.py 实际实现）:                  │
│    paligemma_id = vocab_size - 1 - skip_tokens - fast_token_id   │
│                = 257152    - 1 - 128          - fast_token_id    │
│                = 257023 - fast_token_id                          │
│                                                                  │
│  具体映射:                                                       │
│    FAST token #0   → PaliGemma ID 257023  (倒数第 129 个位置)   │
│    FAST token #42  → PaliGemma ID 256981                        │
│    FAST token #156 → PaliGemma ID 256867                        │
│    FAST token #895 → PaliGemma ID 256128                        │
│                                                                  │
│  为什么"倒着往前用": 最后 128 个位置是 EOS/BOS/padding 等       │
│    特殊 token，不能占用。FAST 从倒数 129 往前租用——             │
│    只要 BPE 词表不超过 ~900 个，就不会和前面的文字 token 冲突   │
│                                                                  │
│  像一栋 25.7 万层大楼——顶上 128 层是特殊用途层（不租），       │
│    FAST 从 129 层往下租了几百层，文字 token 住下面，互不干扰    │
│                                                                  │
│  例: FAST token #156 → PaliGemma token ID 257023                 │
│      FAST token #512 → PaliGemma token ID 257379                 │
│                                                                  │
│  为什么需要这层: VLA 的 backbone 是 PaliGemma——                  │
│    它只能预测自己词表里的 token ID。FAST token 必须映射进去     │
└─────────────────────────────────────────────────────────────────┘
```

### 三层词表的职责分工

| 层 | 谁设计 | 词表大小 | 解决什么问题 |
|:---|:---|:---:|:---|
| **量化字典** | 人工（基于 DCT 系数范围） | ~几十到几百个档位 | 连续 → 离散 |
| **BPE 词表** | 从数据学习 | ~1000-5000 | 原始数值 → 运动语义 |
| **PaliGemma 词表** | Google（预训练 VLM） | 257152 | FAST token → VLA 能预测的 token |

## 三、为什么 FAST 需要这三层，而不是一层？

### 3.1 为什么不能直接把 action 值映射到 PaliGemma 词表？

PaliGemma 的词表是**文字**的词表——token #1000 是 "the"，token #50000 是 "Ġrunning"。如果直接把关节角度映射进去——token #3.14 不存在，也没有任何语义关联。

简单 binning 的做法：把连续角度切成 256 个 bin，每个 bin 分配一个 PaliGemma token ID。问题是 50×32=1600 个值 → 1600 个 token，序列太长太稀疏。

### 3.2 为什么量化之后还要 BPE？

量化只解决"连续→离散"的问题。它产出的整数序列仍然很长、信息密度低——每个整数只是一个"频率分量"，不是完整的"运动概念"。

BPE 把多个相关的频率值合并为一个"运动词"——就像 LLM 把 "t-h-e" 合并为 "the"。模型的注意力机制处理 30 个高信息的 token 比处理 300 个低信息的 token 高效得多。

### 3.3 为什么 BPE 之后还要映射到 PaliGemma 词表？

因为 VLA 的 backbone 是 PaliGemma——一个预训练好的 VLM。它的 embedding 表、LM head 都是 PaliGemma 词表维度的（257152 维）。如果新建一个独立的动作 token 体系，需要重新训练嵌入层——不仅参数多，还损失了预训练权重。

**映射到 PaliGemma 词表 = 复用预训练的基础设施。** FAST token 挂在 PaliGemma 词表的末尾区域——PaliGemma 预训练时没学过这些 token，但通过 fine-tune，它们的 embedding 会从预训练分布中"借力"快速收敛。

## 四、一个完整例子：从关节角到 PaliGemma token ID

**输入**：单关节 10 步 action

```
原始角度: [0.00, 0.16, 0.31, 0.45, 0.59, 0.71, 0.81, 0.89, 0.95, 0.99]
```

| 步骤 | 操作 | 中间结果 | 这一步的"词表" |
|:---|:---|:---|:---|
| **DCT** | 10 点 → 10 个频率系数（连续值） | `[2.93, -1.81, -0.12, 0.03, -0.01, 0.001, ...]` | —（还是连续值） |
| **量化** | 连续小数 → 离散整数 | `[29, -18, -1, 0, 0, ...]` | 量化字典：k0-2 用 0.1 间隔，k3+ 归零 |
| **Flatten** | 展平 + 跳过零 | `[29, -18, -1]` | — |
| **BPE encode** | 合并常见模式 | `[156]`（假设 [29,-18,-1] 在 BPE 词表中是一个 token） | BPE 词表：~1000-5000 个 token |
| **PaliGemma 映射** | BPE token → PaliGemma ID | `[257023]` | PaliGemma 词表：257152 个 token |

**最终结果**：10 个连续角度值 → 1 个 PaliGemma token ID。VLA 的训练目标就是：给定图像和文本 prefix，预测这个 token ID。

对比简单 binning：10 个值 → 10 个 bin token，每个 token ID 相互独立，没有压缩。

## 五、推理时的反向过程

VLA 推理时，自回归生成的每个 token 走反向链路回到动作：

```
模型输出: PaliGemma token ID 257023
    │
    ▼  PaliGemma 词表反向映射
FAST token #156
    │
    ▼  BPE decode（查 BPE 词表）
[29, -18, -1]
    │
    ▼  Unflatten + 补零
[29, -18, -1, 0, 0, 0, 0, 0, 0, 0]
    │
    ▼  逆量化
[2.9, -1.8, -0.1, 0, 0, 0, 0, 0, 0, 0]
    │
    ▼  IDCT
[0.01, 0.17, 0.32, 0.46, 0.58, 0.70, 0.80, 0.88, 0.94, 0.98]
    │
    ▼
机器人执行这 10 步关节角
```

## 六、一句话总结

> **FAST 构建了三层词表——量化字典（连续→离散，人工设计）、BPE 词表（数值→运动语义，从数据学习）、PaliGemma 词表映射（FAST→VLA 基础设施，工程适配）。这就像给机器人动作编了一本"词典"——从"关节角度"查到"运动词汇"再查到"模型认识的数字"，而 LLM 的词典是从"字母"查到"单词"再查到"模型认识的数字"——本质完全相同。**
