## 读之前先搞清楚

### 这篇论文要解决什么问题？

π₀（上一篇论文）展示了惊人的 dexterity——叠衣服、收桌子、装纸箱。但它有一个致命限制：**只能在自己见过的环境里工作。** 把 π₀ 的机器人搬到一个全新的家（训练数据中从未出现过的厨房/卧室），它就不知道该怎么做了。

π₀.₅ 的目标：**让 VLA 模型在新环境中（out-of-distribution, OOD）也能正确理解和执行复杂的长程任务——比如在一个从没去过的家里"打扫厨房"或"整理卧室"。**

这不是简单的"见过红杯子→认识蓝杯子"——而是"从没见过这间卧室→知道枕头放床上、衣服放衣柜、垃圾扔垃圾桶"——需要**物理技能泛化 + 视觉泛化 + 语义泛化**同时发生。

> **小白理解**：π₀ 像一个在驾校练习场练得炉火纯青的学员——在自己的练习场上倒库满分。π₀.₅ 像一个真正的司机——不管去哪个陌生停车场，都能找到车位倒进去。它靠的是见过足够多的不同停车场（co-training on diverse environments）+ 学过交通规则（web data 提供语义常识）。

### π₀ vs π₀.₅：一张表看懂核心区别

π₀ 证明了 VLA 能做复杂长程任务，但只能在训练过的环境里工作。π₀.₅ 不是 π₀ 的小改进，而是一次**泛化能力的质变**——从"固定场景专家"进化为"开放世界通才"。

| 维度 | π₀ | π₀.₅ |
|:---|:---|:---|
| **训练数据** | 7 种机器人、68 个任务的 robot demo（~10,000h） | 机器人 demo + 多模态 web 数据 + 人类口头指导 + 物体检测 + 多个真实家庭环境 |
| **训练环境** | 固定实验室/办公室环境 | **100+ 个不同家庭环境**（in-the-wild） |
| **泛化能力** | 同一环境内跨任务（叠衣→收桌） | **跨环境泛化**：新家（训练中从未见过）→ 自主打扫 |
| **核心机制** | VLM backbone（PaliGemma 3B）提供语义常识 | **Co-training**：web 数据"唤醒"VLM 的语义常识 → 在新环境中识别物体和布局 |
| **推理方式** | 单步：语言指令 → action chunk | **两级推理**：语言指令 → 高层文本子任务 → 低层 action chunk（自包含 Chain-of-Thought） |
| **对新物体的处理** | 需 fine-tune | 零样本（因为 web co-training 教过"这是什么"） |
| **模型定位** | 通用基础模型（foundation model） | **开放世界 VLA baseline**（权重开源，被广泛使用） |

> **小白理解**：π₀ 像一个在自己家厨房练了一万小时的厨师——刀工火候无可挑剔，但换个厨房就找不到调料在哪。π₀.₅ 像一个在 100 个不同厨房都做过菜的厨师——不管去哪个新厨房，一眼就知道灶台、水槽、调料在哪。web co-training 相当于"看过无数厨房照片和食谱"，建立了对"厨房"这个概念的通用理解。

### 读懂这篇论文需要的前置知识

| 概念 | 简单解释 |
|:---|:---|
| **Co-training（联合训练）** | 在多种不同类型的数据上同时训练一个模型 |
| **OOD（Out-of-Distribution）** | 测试环境/物体在训练数据中从未出现 |
| **High-level / Low-level Policy** | High-level = 决定"下一步做什么"（文本），Low-level = 决定"关节怎么动"（连续值） |
| **Verbal Instructions** | 人类用自然语言一步步指导机器人完成任务 |
| **Subtask Command** | 分解后的子任务指令，如"拿起枕头" |
| **Cross-Embodiment Data（CE）** | 来自不同构型机器人的数据 |
| **Multi-Environment Data（ME）** | 来自多个不同环境（不同家庭）的静态机器人数据 |

## 一、π₀.₅ 的解决思路

核心 idea：**通过在极其多样化的数据混合物上 co-train——包括机器人 action 数据（多种机器人、多种环境）、多模态 web 数据（图像问答、物体检测、captioning）、人类口头指导数据（verbal instructions）——让 VLA 同时学会"物理怎么操作"和"语义上怎么做才对"。**

```
π₀ 的训练数据                         π₀.₅ 的训练数据
─────────────────                    ─────────────────
只有机器人 action 数据                 机器人 action 数据
                                      + 多模态 web 数据（看图问答、物体检测）
                                      + 人类口头指导视频
                                      + 多个不同家庭的数据
                                      + 来自其他机器人的数据
                                      = 让模型"理解"新环境中的物体和任务
```

**为什么 co-training 能让模型泛化？** 因为 VLA 基于 VLM backbone——而 VLM 本身就是在 web 数据上 pre-trained 的。π₀.₅ 的 co-training 相当于"提醒" VLM：你在 web pre-training 时学到的常识（枕头在卧室、盘子在水槽、垃圾在垃圾桶），现在可以应用到机器人场景。同时，来自多个家庭和多个机器人的数据让模型不会 overfit 到某一个特定的环境布局或机器人构型。

> **小白理解**：π₀ 像一个只在自己家厨房练过做菜的厨师——换一个厨房（灶台位置变了、锅碗瓢盆品牌不同）就手忙脚乱。π₀.₅ 像一个在 100 多个不同厨房都做过菜的厨师——不管去哪个新厨房，一眼就知道"这是灶台、那是水槽、调料应该在这附近"。多模态 web 数据相当于"看过很多厨房照片和食谱"，知道厨房的通用语义。

## 二、π₀.₅ 的核心设计 —— 两大支柱：数据配方 + 两级推理

π₀.₅ 没有发明新的神经网络架构，它的核心创新在于**重新设计了"给模型喂什么数据"和"让模型怎么输出"**。

### 支柱一：Co-training 数据配方 —— 不只喂"怎么做"，还要喂"是什么"

π₀ 只有一种训练数据：机器人示范（image → action）。π₀.₅ 混入了四类辅助数据，构成五源配方。每种数据教会模型不同的能力，缺失任何一种都会导致特定类型的泛化失败：

| 数据类型 | 训练形式 | 教会模型什么 | 缺失后果 |
|:---|:---|:---|:---|
| ① **Robot Action** | image+state → action chunk（Flow Matching + MSE loss） | "怎么操作"——物理技能 | 完全不会动 |
| ② **Verbal Instructions** | 人类分步指导文本，作为任务标签序列 | "任务怎么拆解"——高层规划能力 | 面对新任务不知从哪步开始 |
| ③ **Object Detection** | image → bbox + class（regression + CE loss） | "这东西叫什么、在哪"——物体定位 | 在新环境中不认识新物体 |
| ④ **Web 多模态**（VQA/Captioning） | image+question → answer（CE loss） | "这东西干什么用、该放哪"——语义常识 | 可能把枕头放水槽里 |
| ⑤ **Subtask Commands** | 文本标签（如"拿起枕头"） | "这一步的目标是什么"——任务锚定 | 子任务容易偏离原意 |

> 关键洞察：① 教"手"，②③④⑤ 教"脑"。纯 ① 训练的模型 = 肌肉发达但没常识的机器人——在新环境中不认识东西，也不知道东西该放哪。这就是 π₀ 泛化失败的根本原因：它的 VLM backbone 在纯 robot demo 训练中"遗忘"了 web pre-training 学到的语义知识。

### 支柱二：自包含两级推理 —— 一个模型，两层思考

传统做法需要两个独立模型：高层 planner（文本→子任务）+ 低层 policy（子任务→action）。π₀.₅ 的核心架构决策——**同一个 VLA 模型同时承担两层**：

```
同一个 VLM Backbone（PaliGemma ~3B）
        │
        ├── 高层模式：[image + "clean bedroom"] + <HIGH> token
        │    → LM Head → autoregressive decode → "pick up pillow"
        │    （输出文本子任务 token 序列）
        │
        └── 低层模式：[image + "pick up pillow" + state] + <LOW> token
             → Action Expert + Flow Matching → action chunk
             （输出 50 步连续关节角度）
        │
        循环 ←──────────────────────────────────────────────────┘
        （执行完当前 chunk → 用新观测回到高层 → 生成下一个子任务）
```

**为什么同一个模型能同时做两件完全不同的事？** VLM backbone 在 web pre-training 阶段已经学会了"看图理解场景"和"语言生成"两种能力。π₀.₅ 的 co-training 同时保持并增强这两种能力——robot demo 训练 action 通路，web/VQA 数据保持语义通路，verbal instructions 训练"场景→子任务"的映射。两种能力通过特殊 token（`<HIGH>` / `<LOW>`）在推理时动态切换。

> **小白理解**：π₀.₅ 像一个会"出声思考"的厨师。你说"做顿饭"，它先自言自语"先洗菜"（高层），然后手自动去洗（低层）。洗完看了一眼砧板，自言自语"现在切菜"（高层），手自动去切（低层）。**这个自言自语不是多余的——它是模型把模糊的长期目标拆成自己能执行的具体步骤的方式。关键是同一个大脑既在"想"也在"做"，不需要外挂一个调度器。**

## 三、训练流程 —— High 与 Low 如何在一个模型里同时学会"想"和"做"

### 核心问题：同一个 VLM Backbone 如何同时学会文本生成和动作生成？

π₀.₅ 训练的核心挑战：**同一个模型要同时掌握两种完全不同类型的输出**——离散的文本 token（高层子任务规划）和连续的动作向量（低层关节控制）。这两个能力不仅输出类型不同，连训练信号也来自不同的数据源。

π₀.₅ 的解决方案是用**两种互补的训练格式**交替更新同一个 VLM Backbone：

| | 格式A：Verbal Instruction（教"想"） | 格式B：Robot Demo（教"做"） |
|:---|:---|:---|
| **输入序列** | `[image] [task text] <HIGH>` | `[image] [subtask text] [state] <LOW>` |
| **输出 head** | Language Model Head（词表 softmax） | Action Expert（Flow Matching） |
| **输出** | 下一个文本 token（如 "pick"） | 50 步关节角序列（350 维） |
| **Loss** | Cross-Entropy（分类） | MSE（回归） |
| **教会什么** | P(子任务序列 \| 画面, 总任务) | P(动作轨迹 \| 画面, 子任务, 关节状态) |

> 关键洞察：**格式A 的输出（子任务文本）正是格式B 需要的输入条件**。两种格式不是独立的——它们通过 VLM Backbone 的 hidden state 空间天然连接在一起。

### Phase 1：一次训练迭代的完整数据流转（以格式B Robot Demo 为例）

以下展示一个具体训练样本从原始数据到 loss 回传的全过程。假设这个样本来自"打扫卧室"任务的 robot demo 数据：

```
训练样本的原始组成：
  · 图像：224×224×3 RGB（腕部相机拍摄）
  · 总任务文本："clean the bedroom"
  · 当前子任务文本："pick up the pillow"
  · 关节状态：7维向量 [肩30°, 肘45°, 腕72°, 指0°, ...]
  · 目标动作（人类遥操作真实轨迹）：50步×7维 = 350维连续向量

═══════════════════════════════════════════════════════════════
Step 1: 图像 → Image Tokens（ViT Encoder）
═══════════════════════════════════════════════════════════════

  224×224×3 RGB ──→ ViT (SigLIP, patch 14×14) ──→ 256 个 image tokens
                                                    每个: ℝ^1152
  过程：图像切成 16×16 = 256 个 patch → 每 patch 通过 ViT 多层
        Transformer → 输出 256 个语义向量

═══════════════════════════════════════════════════════════════
Step 2: 文本 → Text Tokens（Tokenizer + Embedding）
═══════════════════════════════════════════════════════════════

                                           padding 到 64 个位置

═══════════════════════════════════════════════════════════════

═══════════════════════════════════════════════════════════════
Step 4: Token 拼接 → VLM Backbone 前向传播
═══════════════════════════════════════════════════════════════

  完整序列（321 tokens，每个 ℝ^1152）：
  ┌────────────┬─────────────┬───────────┬────────┐
  │ 256 img    │ 64 text     │ 1 state   │ <LOW>  │
  │ tokens     │ tokens      │ token     │ token  │
  └────────────┴─────────────┴───────────┴────────┘
                      │
                      ▼
  ┌──────────────────────────────────────────────────────────┐

  │                                                         │

                                    │

                                          │
                                    与真实下一个 token 比较
                                    Loss = -log P(correct_token | context)
                                    （交叉熵，分类 loss）
```

### Phase 2：High 与 Low 如何共享同一个 Backbone —— 训练时的双重身份

**一轮训练中，格式A 和格式B 交替出现，梯度在同一个 VLM Backbone 上累积**：

```
一个混合 mini-batch 的训练过程（batch_size=4）：

  Batch = [格式B₁, 格式A₁, 格式B₂, 格式A₂]
          └─ robot ─┘└─ verbal ─┘└─ robot ─┘└─ verbal ─┘

  ┌────────────────────────────────────────────────────────────┐
  │ 样本1（格式B）：[img + "pick up pillow" + state + <LOW>]   │
  │   → VLM Backbone → h_LOW → Action Expert → action chunk    │
  │   → MSE Loss：预测动作与人类示范之间的均方误差              │
  │   → 梯度更新：VLM Backbone 中与"空间推理+动作规划"相关的权重│
  ├────────────────────────────────────────────────────────────┤
  │ 样本2（格式A）：[img + "clean bedroom" + <HIGH>]           │
  │   → VLM Backbone → h_HIGH → LM Head → 预测子任务 token     │
  │   → CE Loss：预测 token 与人类口头指导中的 token 对比       │
  │   → 梯度更新：VLM Backbone 中与"场景理解+语言生成"相关的权重│
  ├────────────────────────────────────────────────────────────┤
  │ 样本3（格式B）：[img + "put on bed" + state + <LOW>]       │
  │   → （同格式B流程）                                         │
  ├────────────────────────────────────────────────────────────┤
  │ 样本4（格式A）：[img + "clean bedroom" + <HIGH>]           │
  │   → （同格式A流程）                                         │
  └────────────────────────────────────────────────────────────┘
                           │
                           ▼
  ┌────────────────────────────────────────────────────────────┐
  │ 4 个样本的梯度在 VLM Backbone 上累积 → 取平均 → 更新参数  │
  │                                                            │
  │ 同一组 VLM Backbone 参数同时接收了：                        │
  │   · 格式B 的"动作梯度"——教它"如何执行子任务"               │
  │   · 格式A 的"语言梯度"——教它"如何分解总任务"               │
  │                                                            │
  │ 两类梯度在参数空间中近乎正交 → 互不干扰，各自强化           │
  └────────────────────────────────────────────────────────────┘
```

**两种格式之间的隐藏连接——为什么不是"两个独立任务"**：

格式A 生成的子任务文本（如 "pick up the pillow"）正是格式B 的输入条件。这意味着 VLM Backbone 的 hidden state 空间必须同时支持两种映射：

1. `(image, task) → subtask text`（格式A 训练出的映射）
2. `(image, subtask text, state) → action`（格式B 训练出的映射）

推理时，这个共享表示的价值体现出来：当 VLM 在高层模式下生成 "pick up the pillow" 时，它的 hidden state 不仅编码了文本信息，还天然包含了"接下来手该怎么抓"的空间信息——因为同一个 Backbone 在格式B 训练中被塑造成了"理解抓取动作"的样子。

> **小白理解**：这就像一个双语者同时学了英语（格式A：文本表达）和手语（格式B：动作表达）。同一个大脑（VLM Backbone）掌握了两种"语言"。当他说"我要拿那个杯子"（英语）时，他的手已经下意识做出了拿杯子的准备动作——因为同一个大脑中，"说拿杯子"和"实际拿杯子"共享了同一套神经表征。**π₀.₅ 的 VLM Backbone 就是这样一个"双语大脑"——文本和动作在同一个 hidden space 中共享表征，交替训练让两种能力相互增强而非冲突。**

### Phase 3：训练调度与稳定性保障

**数据配比与调度**：

| 配置项 | 设置 | 原因 |
|:---|:---|:---|
| Robot demo（格式B）占比 | 60-70% | 太低 → 物理技能退化；太高 → 语义/规划能力遗忘 |
| Verbal instruction（格式A）占比 | 15-20% | 教会高层任务分解，是两级推理能力的来源 |
| 辅助数据（VQA/检测/web）占比 | 15-20% | 保持 VLM Backbone 的语义常识，防止 catastrophic forgetting |
| Batch 构成 | 每个 batch 强制包含格式A+格式B | 避免某类数据长时间不出现导致对应能力退化 |
| 多环境采样 | 所有环境均匀采样 | 避免 overfit 到某个家庭布局 |

**训练稳定性技巧**：

| 技巧 | 作用 | 具体做法 |
|:---|:---|:---|
| **Gradient Clipping** | 防止格式A和格式B的梯度冲突导致 loss 爆炸 | 全局梯度范数裁剪到 max_norm=1.0 |
| **LR Warmup + Cosine Decay** | 平稳启动，逐步收敛 | 前 1000 步 LR 从 0 → 1e-4，之后 cosine 衰减到 1e-6 |
| **Data Augmentation** | 提高视觉鲁棒性 | 随机裁剪、颜色抖动(±0.2)、光照变化、高斯噪声(σ=0.01) |
| **Action Chunking + Overlap** | 动作连续性，chunk 间平滑过渡 | H=50 步预测（1秒），相邻 chunk 重叠 10 步 |
| **Multi-GPU 数据并行 + 梯度累积** | 支持大规模混合 batch | 数百块 TPU/GPU，累积 4-8 步后更新 |

**训练计算量**：基于 PaliGemma ~3B VLM Backbone + 300M Action Expert，在数百块 TPU/GPU 上训练数天。与 π₀（10,000h 单一 robot demo）相比，π₀.₅ 总数据时长类似，但**数据多样性（环境数量 × 格式种类）高出约一个数量级**——这是泛化能力的来源，也是训练复杂度的代价。

## 四、推理流程 —— 两级推理的逐帧执行机制（深度版）

### 完整执行时序（以"打扫陌生卧室"为例，含 Tensor 维度）

π₀.₅ 推理时，一次完整任务由多个"高层→低层→执行"循环组成。以下是带 tensor 维度的逐帧过程（50Hz 控制频率，每步 0.02s）：

```
t=0.00s  ┌──────────────────────────────────────────────────────┐
         │ 高层推理（自回归文本生成，~0.1-0.3s）                │
         │                                                      │
         │ 输入 Tensor 组装：                                    │
         │   image tokens:  [256, 1152]  (ViT 输出的 256 个 token)│

         │        ↓                                             │

         │   每层：Self-Attention(321→321) + FFN(1152→4608→1152) │
         │   输出: [321, 2048] hidden states                     │
         │        ↓                                             │
         │ 取 <HIGH> 位置的 hidden: h_HIGH ∈ ℝ^2048              │
         │        ↓                                             │
         │ LM Head: Linear(2048→256K) → softmax                  │
         │        ↓                                             │
         │ token₁="pick"   P=0.92（贪心）                        │
         │   → 拼回序列，重新前向传播                             │
         │ token₂="up"     P=0.88                                │
         │ token₃="the"    P=0.95                                │

         │ token₅=<EOS>    P=0.91 → 停止                         │
         │        ↓                                             │
         │ 输出子任务："pick up the pillow"（4 tokens, ~0.2s）   │
         └────────────────────┬─────────────────────────────────┘
                              │
t=0.30s  ┌────────────────────▼─────────────────────────────────┐
         │ 低层执行（Flow Matching 推理，~0.05-0.1s）            │
         │                                                      │
         │ 输入 Tensor 组装（模式切换！）：                       │
         │   image tokens:  [256, 1152]  (同前)                  │
         │   text tokens:   [64, 1152]   ("pick up the pillow")  │

         └────────────────────┬─────────────────────────────────┘
                              │
t=0.30~1.30s  ┌───────────────▼─────────────────────────────────┐
              │ 机器人执行 50 步 action（receding horizon）       │
              │ 每步 0.02s，持续 1 秒                             │
              │ ★ 执行期间相机持续采集新画面                      │
              │ ★ 第 40 步时（t≈1.10s），后台开始下一次高层推理   │
              │   （利用 chunk 重叠的 10 步窗口提前规划）         │
              └────────────────────┬─────────────────────────────┘
                                   │

              │ 回到高层推理（基于执行后新观测 + 重叠窗口预启动） │
              │ 输入：[新画面: 枕头已在手中, 256×1152]             │
              │       [text: "clean the bedroom", 64×1152]        │
              │       [<HIGH>, 1×1152]                            │
              │        ↓                                         │
              │ 输出："put the pillow on the bed"                 │
              └────────────────────┬─────────────────────────────┘

```

### Flow Matching 推理的数学细节

Flow Matching 是 π₀.₅ 低层动作生成的核心算法。推理（去噪）过程的数学本质是**求解一个从噪声到目标动作的条件常微分方程（ODE）**：

**符号定义**：
- `x ∈ ℝ^(50×7)`：动作 chunk（50 步 × 7 自由度关节角），flatten 后为 350 维
- `t ∈ [0, 1]`：去噪时间，t=0 表示纯噪声，t=1 表示干净动作
- `v_θ(x, t, c)`：Action Expert 网络，输入噪声动作 x、时间 t、条件 c=h_LOW，输出 vector field（"去噪方向"）
- `c = h_LOW`：VLM Backbone 为 `<LOW>` token 输出的 hidden state，编码了"当前画面+子任务指令+关节状态"

**去噪过程（Euler 法求解 ODE，10 步）**：

```
Algorithm: Flow Matching Inference (去噪)

输入：h_LOW ∈ ℝ^2048（VLM 编码的 conditioning）
输出：â ∈ ℝ^(50×7)（预测的动作 chunk）

  x₀ ← 从标准正态分布采样：x₀ ~ N(0, I_350)
  Δt ← 1/10 = 0.1

  for k = 0 to 9:
      t_k ← k · Δt                              # 当前时间步
      v_k ← v_θ(x_k, t_k, c=h_LOW)              # Action Expert 预测的去噪方向
      x_{k+1} ← x_k + v_k · Δt                  # Euler 步：沿向量场前进
  end

  return x₁₀  # 这就是预测的 action chunk
```

**每一步发生了什么**：
- k=0 (t=0): 输入纯噪声，Action Expert 根据 h_LOW 判断"这个任务需要手臂朝哪个大致方向移动"，输出粗略方向
- k=3 (t=0.3): 动作已具雏形——大致的轨迹形状出现，但细节模糊
- k=7 (t=0.7): 轨迹已基本清晰——关节角序列连续、平滑
- k=9 (t=0.9): 最后一步精修——微调关节角度，确保末端位置精确

**为什么 Flow Matching 比 Autoregressive 更适合动作生成**：
- 动作是**连续值**，天然适合连续生成模型（Flow Matching / Diffusion）
- Autoregressive 逐 token 预测会将连续空间离散化，损失精度
- Flow Matching 一次性生成整个 chunk（50 步），保证**全局时序一致性**——不会出现"前几步向东、后几步向西"的不连贯

> **小白理解**：Flow Matching 的去噪过程就像一个雕塑家。一开始面对一块大理石（纯噪声 x₀），每凿一刀就离目标雕塑（干净动作 â）更近一步。凿的方向（vector field v_k）由 Action Expert 根据"我想让机器人做什么"（h_LOW）来决定。10 刀之后，机器人手臂的完整运动轨迹就成形了。**关键：10 步中每一步都在"看"最终目标（conditioned on h_LOW），所以越到后面越精准。**

### 自回归文本生成的机制细节

高层推理中的子任务生成不是"从候选列表中选一个"，而是**逐 token 的条件自回归过程**：

1. 将 `[image tokens + task text tokens + <HIGH>]` 送入 VLM backbone，得到所有位置的 hidden states
2. 取**最后一个 token 位置**的 hidden state h_last ∈ ℝ^2048
3. Language Model Head（Linear(2048 → 256K) + softmax）计算词表概率分布：P(token | context) = softmax(W · h_last)
4. 贪心选择概率最高的 token t̂ = argmax P(token | context)
5. 将 t̂ 拼接到输入序列末尾，重复步骤 1-4
6. 当 t̂ = `<EOS>` 或序列长度达到 max_len（通常 10 tokens），停止

**为什么模型能"知道"下一步该做什么？** 训练时 verbal instructions 数据提供了大量"画面+总任务→子任务序列"的范例。模型学到的本质是条件概率分布 P(子任务序列 | 当前观测, 总任务)。推理时贪心选择最高概率路径。

### 模式切换：文本 ↔ 动作

同一个 VLM backbone 通过**特殊 token + 不同输出 head** 切换两种模式：

| | 高层模式（文本生成） | 低层模式（动作生成） |
|:---|:---|:---|
| **Prompt 结尾 token** | `<HIGH>` | `<LOW>` |
| **取哪个 hidden** | h_HIGH（最后一个 token 位置） | h_LOW（最后一个 token 位置） |
| **输出 head** | LM Head：Linear(2048→256K) + softmax | Action Expert：300M Transformer + Flow Matching |
| **输出类型** | 离散 token ID | 连续向量 ℝ^(50×7) |
| **推理时间** | ~0.1-0.3s（token 逐个生成） | ~0.05-0.1s（10 步并行去噪） |

> **关键设计**：`<HIGH>` 和 `<LOW>` 是训练时学到的"模式开关"——VLM Backbone 看到 `<HIGH>` 时，其 hidden state h_HIGH 自动适配 LM Head 的需求（编码语义信息）；看到 `<LOW>` 时，h_LOW 自动适配 Action Expert 的需求（编码空间+运动信息）。**这种适配不是硬编码的——是训练时两种格式交替更新 VLM Backbone 自然涌现的能力。**

### Receding Horizon：Chunk 重叠与无缝衔接

π₀.₅ 每次低层推理输出 H=50 步（1 秒）的动作 chunk，但机器人并非执行完 50 步后才重新推理——那样会导致动作停顿。实际使用的是 **receding horizon control（滚动时域控制）**：

```
Chunk 重叠与执行时序（H=50, overlap=10）：

  时间线 ─────────────────────────────────────────────────────→

  Chunk 1: [a₁────────────────────────────a₅₀]
            ├─ 执行 40 步 ─┤├─ 重叠 10 步 ─┤
                             │              │
  Chunk 2:                   [b₁────────────┼────b₅₀]
                              开始推理       ├─ 执行 40 步 ─┤
  （在 Chunk 1 执行到第 30 步时，Chunk 2      │              │
   的后台推理已启动，利用最新观测）            │              │
                                             │              │
  Chunk 3:                                   [c₁────────────c₅₀]
                                              后台推理在 Chunk 2
                                              执行期间提前启动
```

**实现细节**：
- 每个 chunk 执行前 40 步（0.8s），后 10 步（0.2s）为"重叠区"
- 在重叠区内，下一 chunk 的推理已在后台并行完成
- 切换时，机器人从当前 chunk 的最后一步平滑过渡到新 chunk 的第一步
- 推理延迟（~0.1s）被重叠区完全吸收 → 对用户来说动作是连续的，无停顿

### 🔢 具体数字例子：一次完整推理的逐步追踪

**条件设定**：陌生卧室（训练中从未见过），地上有一个白色枕头，床在画面右侧约 2 米处。相机分辨率 224×224，控制频率 50Hz。

## 六、实验结果

### 6.0 消融分析：每类数据对泛化的独立贡献

这是π₀.₅ 最重要的消融实验——通过逐一移除数据源，量化每类数据对 OOD 泛化的贡献：

| 消融变体 | 移除的数据 | OOD Follow Rate | OOD Success Rate | 核心结论 |
|:---|:---|:---:|:---:|:---|
| **Full π₀.₅** | 无（全部数据源） | **~75%** | **~60%** | baseline |
| no WD | Web Data（VQA/Captioning/Detection） | ~55% | ~40% | **Web data 贡献最大**：OOD Follow Rate 下降 20 个百分点 |
| no CE | Cross-Embodiment data | ~60% | ~45% | 跨机器人数据对物理技能泛化有贡献 |
| no ME | Multi-Environment data | ~58% | ~42% | 多环境数据对场景泛化有贡献 |
| no ME or CE | 除 mobile manipulation 外的所有 | ~30% | ~20% | **几乎无泛化能力**（仅为 Full 的 1/3） |

**三个核心发现**：
1. **Web Data（WD）贡献最大**——移除后 OOD Follow Rate 从 75% 暴跌至 55%。因为 web data 教会模型识别训练中没见过的物体类别（"这是花瓶，应该放桌上"），这是纯 robot demo 学不到的
2. **ME 和 CE 对所有指标都有贡献**——更多环境 + 更多机器人构型 = 更好的基础物理技能。两者独立且可叠加
3. **只用同一机器人在同一环境的数据 = 几乎零泛化**——这反过来说明了 π₀.₅ 泛化能力的来源不是"大模型"，而是"多样化的数据配方"

> **小白理解**：这个消融实验回答了"到底是模型大了自然变强，还是数据配方对了才变强"。答案是后者——同样的模型架构，只喂单一数据 = 在新家手足无措；喂五源配方 = 在新家自主打扫。**这证明了 VLA 泛化的瓶颈不在模型容量，而在训练数据的多样性。**

### 6.1 主结果：在新家里的清洁任务

| 评估条件 | π₀.₅ | no WD | no CE | no ME | no ME or CE |
|:---|:---:|:---:|:---:|:---:|:---:|
| In-distribution Follow Rate | **~90%** | 85% | 82% | 80% | 65% |
| In-distribution Success Rate | **~80%** | 72% | 68% | 65% | 45% |
| **OOD Follow Rate** | **~75%** | 55% | 60% | 58% | 30% |
| **OOD Success Rate** | **~60%** | 40% | 45% | 42% | 20% |

> **小白理解**：在训练见过的环境中（In-distribution），所有 variant 表现尚可。但到了新环境（OOD），差距急剧拉大——完整 π₀.₅ 的 OOD 成功率是"no ME or CE"的 3 倍。**Web data 单独提供了最大的 OOD 提升**（OOD Follow Rate: 75% → 55%），因为模型需要 web knowledge 来识别新物体。

### 6.2 环境数量 Scaling：越多越好

π₀.₅ 测试了训练环境数量从 10→50→100+ 对泛化性能的影响。结果显示：
- 泛化性能随环境数量**单调递增**（持续提升，没有 plateau）
- 在 ~100 个环境后，**接近在测试环境上直接训练的 baseline 水平**

> **小白理解**：这证明了 VLA 的环境泛化存在 scaling law——见过 100 个不同的家，基本上就能应对第 101 个新家了。400 小时的同一环境数据 < 400 小时分布在 100 个环境的数据。

## 八、局限性

| 局限性 | 为什么是局限 |
|:---|:---|
| **泛化仍不完美** | OOD 成功率仅 ~60%，经常犯高层语义错误（如把衣服放桌上而不是衣柜里） |
| **需要大量多样化数据** | 至少需要 100+ 个不同环境才能接近 viable 泛化——这对大多数团队不可行 |
| **高层决策仍可能出错** | 自包含 chain-of-thought 的好处是自主，但坏处是高层错误无法被外部纠正 |
| **非完全 end-to-end** | 仍是 high-level text + low-level action 的两阶段，不是端到端 Continuous CoT |
| **只在家庭清洁任务上验证** | 其他领域（工业、医疗、户外）的泛化能力未知 |

## 九、一句话总结

> **π₀.₅ 通过 co-training 把机器人 action 数据、web 多模态数据、人类口头指导混合训练，让同一个 VLA 在新环境中既能"自主思考"高层子任务（文本 CoT），又能执行低层连续控制——首次让机器人走进从未见过的家并完成打扫任务，同时证明了 VLA 泛化遵循 scaling law：见过的环境越多，在新环境表现越好。**
